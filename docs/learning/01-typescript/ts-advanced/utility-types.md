# TypeScript Advanced - Utility Types

Your BookShelf `Book` interface has seven properties: `id`, `title`, `author`, `isbn`, `isAvailable`, `createdAt`, and `updatedAt`. When a user creates a new book, the request should not include `id`, `createdAt`, or `updatedAt` because those are generated by the server. When a user updates a book, every field should be optional because they might only change the title. When you display search results, you only need `id`, `title`, and `author`.

You could define three separate interfaces for these cases. But they would all borrow properties from `Book`, and when you add a new field to the base interface, you would have to update every variation by hand. If you miss one, the types go out of sync silently.

This is where **Utility Types** come in, which are built-in generics that derive new types from existing ones. They take a source type and return a transformed version of it. These utility types are not special syntax. They are regular generic types, just like the `ApiResponse<T>`. TypeScript ships them as part of the standard library. Understanding them is partly about learning what each one does, but more importantly about recognizing when your code is duplicating a type definition and reaching for the right transformation instead.

## Partial and Required

`Partial<T>` takes a type and makes every property optional. This is useful for update operations where the caller sends only the fields they want to change:

```typescript
interface Book {
  id: number;
  title: string;
  author: string;
  isbn: string;
  isAvailable: boolean;
  createdAt: Date;
  updatedAt: Date;
}

type BookUpdate = Partial<Book>;
```

`BookUpdate` has the same properties as `Book`, but each one has a `?` modifier. A function that applies updates can accept any subset of fields:

```typescript
function updateBook(id: number, changes: Partial<Book>): void {
  // changes might have title, or author, or both, or neither
}

updateBook(1, { title: "Clean Code, 2nd Edition" });
updateBook(1, { isAvailable: false, title: "Refactoring" });
```

`Required<T>` does the opposite. It removes the `?` modifier from every property, making all fields mandatory. This is useful when a configuration type has optional fields during setup but must be fully resolved before use:

```typescript
interface AppConfig {
  port?: number;
  debug?: boolean;
  dbUrl?: string;
}

type ResolvedConfig = Required<AppConfig>;
```

`ResolvedConfig` requires all three properties. Passing an object with any of them missing causes a compile error.

`Readonly<T>` is a related utility that marks every property as `readonly`, preventing reassignment after creation:

```typescript
type FrozenBook = Readonly<Book>;

const book: FrozenBook = {
  id: 1,
  title: "Clean Code",
  author: "Robert C. Martin",
  isbn: "978-0132350884",
  isAvailable: true,
  createdAt: new Date(),
  updatedAt: new Date(),
};

book.title = "New Title";
// Compile error: cannot assign to 'title' because it is a read-only property
```

> **_:bulb: Good to know:_** `Readonly<T>` is the type-level equivalent of `Object.freeze()`. The runtime function prevents changes at execution time; the utility type prevents them at compile time.

## Pick and Omit

`Pick<T, K>` constructs a new type by selecting specific properties from the source type. `K` is a union of property names.

A search results page only needs the book's ID, title, and author. Rather than writing a new interface with three properties, pick them from `Book`:

```typescript
type BookPreview = Pick<Book, "id" | "title" | "author">;
```

`BookPreview` has exactly those three properties with the same types they have in `Book`. If you later change `id` from `number` to `string` in `Book`, `BookPreview` reflects the change automatically.

`Omit<T, K>` is the inverse. It constructs a new type by removing specific properties. A creation payload should exclude server-generated fields:

```typescript
type BookCreatePayload = Omit<Book, "id" | "createdAt" | "updatedAt">;
```

`BookCreatePayload` has `title`, `author`, `isbn`, and `isAvailable`. These are exactly the fields the client should provide. The server-side fields are excluded.

> **_⚠ Watch out:_** The property names in `K` must actually exist in `T`. A misspelled key like `"Id"` instead of `"id"` causes a compile error. This is a feature: it catches typos before they reach production.

## Record

`Record<K, T>` creates an object type where every key is of type `K` and every value is of type `T`. It is useful for lookup tables, dictionaries, and maps.

A BookShelf lookup table indexed by ISBN:

```typescript
type BookLookup = Record<string, Book>;

const catalog: BookLookup = {
  "978-0132350884": {
    id: 1,
    title: "Clean Code",
    author: "Robert C. Martin",
    isbn: "978-0132350884",
    isAvailable: true,
    createdAt: new Date(),
    updatedAt: new Date(),
  },
};
```

When `K` is a union of string literals, `Record` enforces that every key in the union is present:

```typescript
type Shelf = "fiction" | "non-fiction" | "technical";
type ShelfCounts = Record<Shelf, number>;

const counts: ShelfCounts = {
  fiction: 120,
  "non-fiction": 85,
  technical: 200,
};
```

Omitting any of the three shelf names causes a compile error. `Record` guarantees that every key in the union has a corresponding value.

## Composing utility types

Utility types can be nested to express more specific transformations. A book update payload should exclude server-generated fields AND make the remaining fields optional:

```typescript
type BookUpdatePayload = Partial<Omit<Book, "id" | "createdAt" | "updatedAt">>;
```

Read this from the inside out: first `Omit` removes three properties, then `Partial` makes the remaining ones optional. The result is a type where `title`, `author`, `isbn`, and `isAvailable` are all present but none of them are required.

Here is the full BookShelf type layer built from a single `Book` definition:

```typescript
interface Book {
  id: number;
  title: string;
  author: string;
  isbn: string;
  isAvailable: boolean;
  createdAt: Date;
  updatedAt: Date;
}

// POST /books: excludes server-generated fields
type BookCreatePayload = Omit<Book, "id" | "createdAt" | "updatedAt">;

// PATCH /books/:id: excludes server fields, everything else optional
type BookUpdatePayload = Partial<Omit<Book, "id" | "createdAt" | "updatedAt">>;

// GET /books (list view): only the fields needed for display
type BookPreview = Pick<Book, "id" | "title" | "author">;

// Application state
interface AppState {
  books: Book[];
  isLoading: boolean;
  filterByAuthor: string | null;
}
```

Five types derived from one interface. When `Book` gains a `publisher` field, the create payload automatically includes it, the update payload makes it optional, and the preview stays unchanged. Nothing drifts.
