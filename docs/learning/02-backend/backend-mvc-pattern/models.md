# Backend Architectures - Models

After routes and controllers move into their own files, the controllers still touch the file system directly. They call `fs.readFileSync`, parse the JSON, filter through the result, and sometimes write the array back. Every controller that needs data repeats this pattern. The path to the JSON file gets hardcoded in several places, and the shape of the data is assumed wherever it is read. If the file moves, or if the storage later changes to a database, every controller that touches data has to be rewritten.

A model is a module that owns data access and the rules around the data. It exports functions like `getAllPosts`, `getPostBySlug`, and `writePosts`. Code that needs data calls those functions and gets back plain JavaScript values. Where the data actually lives is the model's business.

The payoff comes in two places. Controllers get simpler because they stop containing file-system code and start reading like a list of decisions about requests. And changing the data source becomes a single-file change: the same model interface can be backed by a JSON file today and a database tomorrow, and nothing outside the model needs to know.

The model is also where data-shaping rules belong. Generating a slug from a title, sorting posts by date, finding a post by some field: these describe what the data does, not what a particular request needs. They live in the model so that every controller gets the same answer.

## Encapsulating data access

A model module exposes a small set of named functions. Each function does one thing. Internally, the module holds whatever it needs to do its job: file paths, helper functions, type definitions. None of that leaks out.

```typescript
import fs from "fs";
import path from "path";

export interface Post {
  title: string;
  image: string;
  author: string;
  createdAt: number;
  teaser: string;
  content: string;
}

const postsFilePath = path.join(__dirname, "..", "data", "posts.json");
```

Two design choices to highlight:

- The `Post` interface is exported so that controllers and templates can refer to the same shape. There is one source of truth for what a post looks like.
- The file path is a module-level constant. Controllers do not know about it, and changing the storage location later means editing one line.

## Reading and writing the JSON file

The model exposes one function to read all posts and one function to overwrite the file with a new list. Other operations build on these two.

```typescript
export function getAllPosts(): Post[] {
  const raw = fs.readFileSync(postsFilePath, "utf8");
  return JSON.parse(raw) as Post[];
}

export function writePosts(posts: Post[]): void {
  fs.writeFileSync(postsFilePath, JSON.stringify(posts, null, 2), "utf8");
}
```

`getAllPosts` reads the file synchronously, parses the JSON, and returns a typed array. Synchronous I/O is acceptable here because the dataset is small and the trade-off is simpler code. In a high-traffic application, the asynchronous variants would be a better fit.

`writePosts` takes a full array and writes it back. The challenge endpoints that create, update, or delete posts will read the array, modify it, and call `writePosts` to persist the change. Keeping the write operation as a single replace-the-whole-file function is fine for the small JSON file used here.

## Slug lookup

Most blog operations need to find a post by its URL slug. A slug is a URL-safe version of the post title, generated by lowercasing the text and replacing non-alphanumeric runs with dashes. The model owns rules like this so that every part of the app derives slugs the same way.

```typescript
export function slugify(title: string): string {
  return title
    .toLowerCase()
    .replace(/[^a-z0-9]+/g, "-")
    .replace(/^-|-$/g, "");
}

export function getPostBySlug(slug: string): Post | undefined {
  return getAllPosts().find((post) => slugify(post.title) === slug);
}
```

`slugify` is exported because templates and controllers may need it too: a list page needs to build the link for each post, for example. `getPostBySlug` reads all posts, then returns the one whose slug matches, or `undefined` if no post matches. The controller that uses it decides what to do when the result is `undefined`, usually by returning a 404.
